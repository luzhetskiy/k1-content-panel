# Веб-сервис управления контентом сайтов — дизайн

Дата: 2026-08-04
Статус: на утверждение
Базовые документы: `directions/project-overview.md`, `directions/content-standards.md`,
`orchestration/articles-plan.md`

## 1. Задача

Перевести два существующих процесса — «Статьи» и «Строители» — из режима «агент в CLI
на машине владельца» в веб-сервис, которым пользуются 2–3 сотрудника компании,
обслуживая 10+ сайтов.

**Ключевое изменение архитектуры.** Сегодня «умную» часть работы (выбор тем, написание
текстов, формулировка промптов для картинок) выполняет агент в диалоге, а Python-скрипты
служат только «руками». В сервисе интеллект переезжает в **RouterAI**: сервис сам
обращается к модели по сохранённым промптам. Это не перенос кода, а замена
исполнителя — и главный источник риска (см. §15).

### Границы

**Входит:** авторизация и роли, управление сайтами и их ключами, раздел статей,
раздел строителей, глобальные настройки RouterAI, редактируемые промпты с тестовым
прогоном, журнал фоновых задач с учётом расхода.

**Не входит:** телеграм-бот, WebSocket/SSE (достаточно поллинга), WYSIWYG-редактор
готового HTML (правки делаются в админке сайта), автоматическая публикация — всё
создаётся черновиком, как сейчас.

### Порядок реализации

| План | Содержание | Файл |
|---|---|---|
| 1 | Каркас (авторизация, роли, сайты, настройки, промпты, журнал) + раздел «Статьи» + деплой | `orchestration/2026-08-04-plan1-core-and-articles.md` |
| 2 | Раздел «Строители» + миграция `companies.db` в Postgres | пишется после сдачи плана 1 |

План 1 самодостаточен: по его завершении сотрудники уже работают со статьями на всех
сайтах, а строители продолжают идти через CLI до сдачи плана 2.

## 2. Что меняется относительно текущего процесса

| Этап | Сегодня | В сервисе |
|---|---|---|
| Выбор тем | Агент предлагает в чате, тематику знает из разговора | RouterAI по промпту `topics` + описание тематики и тон сайта из его карточки, дедуп по API |
| Согласование тем | Реплика в чате | Экран партии: правка/удаление/добавление тем, кнопка «Запустить» |
| Написание текста | Агент пишет сам, ориентируясь на эталонную статью | RouterAI по промпту `article_body` + закешированный HTML эталонной статьи |
| Сколько картинок | Агент решал по месту | Считается по эталону: сколько `<img>` в нём, столько и генерируется |
| Картинки | `gen_images.py` по ручному манифесту | Тот же RouterAI-вызов, манифест строится сервисом из промпта `content_image` |
| Обложка | Не автоматизирована (пункт 1 «Осталось доделать») | Промпт `cover`, генерация по теме статьи, без водяного знака |
| Водяной знак | Не реализован (пункт 2) | Pillow-наложение на контентные картинки, файл знака — на карточке сайта |
| Загрузка файлов | `filemanager.py` из CLI | Тот же модуль внутри бэкенда |
| Публикация | `publish_articles.py` по JSON-манифесту | Celery-задача, статус и ссылка видны в UI |
| Настройки сайта | Память агента + `.env` | Таблица `sites`, токены шифруются Fernet |

Пункты 1–5 раздела «Осталось доделать» из `orchestration/articles-plan.md` закрываются
этим планом целиком — отдельно доделывать CLI-версию не нужно.

### Терминологическая развилка

Слово «тизер» в проекте означает две разные сущности. В сервисе они называются
по-разному, и путать их нельзя:

- **Обложка статьи** — `teaser_image` у `staticpages`, ImageField страницы. Задаётся
  только multipart-загрузкой в эндпоинт страницы, путём-строкой не задаётся.
- **Карточка-тизер услуги** — запись в `/api/v1/addresses-services/` с полями
  `category`/`city`/`location`. Относится к процессу «Строители» (шаг 6), к статьям
  отношения не имеет.

## 3. Архитектура и стек

```
execution/
  backend/app/      FastAPI + Celery в одном образе
  frontend/         React + Vite + TypeScript + Ant Design
  docker-compose.yml, docker-compose.prod.yml
```

Оба слоя копируют устройство `inntec-inbox` — там этот каркас уже отлажен и
задеплоен, переиспользуется не идея, а конкретный код.

**Backend.** FastAPI 0.115, **синхронный** (сессия `SessionLocal` на запрос, без
async/await) — как в образце, чтобы не делить кодовую базу на два стиля
конкурентности. SQLAlchemy 2.0, Alembic, PostgreSQL 16, Celery + Redis для длинных
задач (генерация картинки — 40–140 секунд, партия из 10 статей — до часа).
Python 3.12 в образе: системный 3.9 на машине владельца больше не ограничивает.

**Frontend.** React 18 + Vite 5 + TypeScript 5 + antd 5 + axios + dayjs. Тема и
layout переносятся из `nst-tg-monitor` **без смены акцента** — `colorPrimary`
остаётся `#dca34c`, вместе с производными оттенками (`#fef8ee` фон выбранного пункта
меню, `#e8b96a`/`#b87c28` для графиков), нейтральной палитрой (`#f4f4f5`, `#ffffff`,
`#18181b`/`#3f3f46`/`#71717a`, границы `#e4e4e7`/`#f0f0f0`) и радиусами 8/12.
Копируются `App.tsx` (Sider + мобильный Drawer), `index.css`, `main.tsx` с `ruRU`.

**Существующий код.** `execution/filemanager.py` и `execution/articles/gen_images.py`
переносятся в бэкенд как модули (`app/sites/filemanager.py`, `app/ai/images.py`) с
заменой `os.getenv`/`load_dotenv` на параметры из БД. CLI-скрипты `step*.py` остаются
в репозитории нетронутыми до сдачи плана 2 — до тех пор строители идут по-старому.

## 4. Роли и доступ

Две роли, как в образце: `admin` и `manager`.

| Раздел | manager | admin |
|---|---|---|
| Статьи (партии, темы, запуск, просмотр) | да | да |
| Строители (план 2) | да | да |
| Сайты — просмотр списка и выбор | да | да |
| Сайты — создание, правка, ключи, промпты сайта | нет | да |
| Промпты (глобальные шаблоны) | нет | да |
| Настройки RouterAI и ключи | нет | да |
| Пользователи | нет | да |
| Журнал задач | да (все записи) | да |

Разделения доступа по сайтам нет — все сотрудники доверенные (решение владельца от
2026-08-03). Поэтому `sites` не связан с `users`.

Механика авторизации переносится из `inntec-inbox` целиком: `POST /api/auth/login`
через `OAuth2PasswordRequestForm`, bcrypt напрямую (не через passlib), JWT в
`httpOnly`-cookie, `JWT_SECRET` из переменной окружения. Сохраняется и защита от
тайминг-атаки: `verify_password` вызывается всегда, даже когда пользователя нет —
против hash-заглушки. Проверка роли — зависимостью `require_role("admin")` на каждом
запросе; скрытие пунктов меню на фронте это UX, не защита.

Первый администратор создаётся скриптом `create_admin.py` с интерактивным вводом
пароля — через UI создать первого админа нельзя.

## 5. Модель данных

```
users              id, email, full_name, password_hash, role, is_active
settings           key, value, is_secret            — глобальные, секреты Fernet
sites              карточка целевого сайта (ниже)
prompt_templates   key, site_id (NULL = глобальный дефолт), text
article_batches    партия статей: сайт, количество, статус, автор
articles           одна статья: тема, slug, html, статус, ссылка на сайте
article_images     картинки статьи: роль, промпт, локальный и удалённый путь
job_runs           журнал фоновых задач: тип, параметры, статус, лог, стоимость
llm_usage          расход RouterAI: модель, токены, стоимость, привязка к job_run
```

### `sites`

| Поле | Назначение |
|---|---|
| `name`, `domain`, `base_url` | идентификация; `domain` уникален |
| `api_token` | токен сайта, шифруется Fernet, в API отдаётся маскированным |
| `publish_target` | `pages` (staticpages) или `articles` |
| `articles_parent_id` | id родительской страницы, под которой лежат все статьи. Раздел произвольный — `/blog/` частный случай, не требование |
| `articles_url_prefix` | url раздела, **вычисляется** из родительской страницы при синхронизации, вручную не вводится |
| `site_description` | о чём сайт, какая тематика, для какой аудитории — основа для подбора тем |
| `tone_of_voice` | требуемый тон контента |
| `reference_article_id` | id эталонной опубликованной статьи — живой шаблон. **Обязателен**: без него статьи для сайта не генерируются |
| `reference_html`, `reference_images`, `reference_synced_at` | кеш эталона: его HTML, число `<img>` в нём и время синхронизации |
| `image_style_prompt` | постоянный стиль контентных картинок сайта |
| `cover_mode` | `like_existing` (ориентир — существующие обложки) или `prompt` |
| `cover_style_prompt` | стиль обложки при `cover_mode = prompt` |
| `watermark_path` | загруженный PNG водяного знака; пусто — знак не накладывается |
| `builder_*` (план 2) | шаблон `builders.html`, `parent_id`, `teaser_category_id`, `teaser_city_id`, `teaser_location_id` |
| `is_active` | скрывает сайт из выпадающих списков, не удаляя историю |

Значения `teaser_category_id`/`city`/`location` для четырёх уже работающих сайтов
берутся из `directions/`-таблицы проекта при первичном заполнении (bolars.ru 3/1/1,
bolars-shop.ru 4/1/1, vetonit-center.ru 3/1/1, stroybaza-samara.ru 3/2/1).

### Синхронизация эталона

Эталонная статья — единственный источник разметки: отдельного HTML-шаблона в сервисе
нет. Одна кнопка на карточке сайта, «Проверить и синхронизировать», делает три вещи
за один заход:

1. запрашивает родительскую страницу `articles_parent_id` и берёт её `url` в
   `articles_url_prefix` — так раздел не может разъехаться с тем, что реально на сайте,
   и администратору не нужно вводить префикс руками;
2. запрашивает эталонную статью и кладёт её `text` в `reference_html`;
3. считает в ней теги `<img>` и пишет результат в `reference_images` — **столько
   контентных картинок и генерируется**. Отдельной настройки «сколько картинок» нет:
   шаблон и есть ответ на этот вопрос.

Дальше эталон берётся из кеша, без обращения к сайту. Кнопка нажимается заново, когда
эталонную статью на сайте отредактировали.

**Про экономию.** Кеш убирает один HTTP-запрос на статью — это мелочь. Настоящая цена
эталона в другом: его HTML целиком уходит во входные токены **каждого** запроса
`article_body`, и кеширование этого не меняет. Если эталон окажется тяжёлым и счёт за
текст станет заметным, снижать надо не число запросов, а объём: подавать в промпт не
полный HTML, а скелет разметки (теги и классы без текстового содержимого). Это отдельная
оптимизация, в план 1 она не входит — сначала нужно увидеть реальные цифры в журнале.

### `articles` — статусы

```
draft         тема согласована, работа не начата
generating    выполняется фоновая задача
generated     html и картинки готовы, страница ещё не создана
published     черновик создан на сайте (published=false на стороне сайта)
failed        ошибка, текст в error_text, доступна повторная попытка
```

`published` означает «создан черновик на сайте» — окончательную публикацию по-прежнему
делает менеджер руками в админке сайта.

### `article_batches` — статусы

```
topics_pending   идёт генерация списка тем
topics_review    темы готовы, ждут согласования менеджером
running          статьи генерируются
done             все статьи в published или failed
failed           не удалось получить темы
```

## 6. Настройки и секреты

Все секреты — токены сайтов и ключ RouterAI — хранятся в БД зашифрованными Fernet.
Переносится `app/settings/crypto.py` из образца целиком: `encrypt`/`decrypt`/`mask`,
`SecretDecryptionError` при смене `ENCRYPTION_KEY`, маскирование `abc...wxyz` при
отдаче в API. Реальное значение секрета не возвращается наружу никогда; при `PUT`
пустая строка означает «не менять».

`ENCRYPTION_KEY` и `JWT_SECRET` — переменные окружения, не настройки в БД.

Глобальные настройки RouterAI (раздел «Настройки», только admin):

| Ключ | По умолчанию | Комментарий |
|---|---|---|
| `routerai_base_url` | `https://routerai.ru/api/v1` | OpenAI-совместимый эндпоинт для текста |
| `routerai_api_key` | — | секрет |
| `text_model` | `anthropic/claude-sonnet-4-6` | модель для тем и текстов |
| `image_model` | `openai/gpt-image-2` | модель картинок |
| `image_quality` | `medium` | `high` дороже втрое: ≈16.8 против ≈5.4 за 1536×1024 |
| `image_size` | `1536x1024` | модель игнорирует `aspect_ratio`, нужные пропорции даёт кроп |
| `image_workers` | `4` | параллельных генераций внутри одной задачи |
| `llm_max_retries` | `3` | повторяются только сбои транспорта |

Текст идёт через OpenAI-совместимый клиент (`openai` SDK, как в `inntec-inbox`),
картинки — через собственный `POST /api/v1/images` с ответом `data[0].b64_json`;
это две разные обёртки над одним провайдером.

## 7. Промпты

Четыре редактируемых шаблона (Jinja2, `SandboxedEnvironment`):

| Ключ | Что генерирует | Переменные |
|---|---|---|
| `topics` | JSON-массив из N тем | `count`, `site_name`, `site_description`, `tone_of_voice`, `existing_titles` |
| `article_body` | HTML статьи | `topic`, `site_name`, `site_description`, `tone_of_voice`, `reference_html`, `image_count`, `image_paths` |
| `cover` | промпт для обложки | `topic`, `cover_style` |
| `content_image` | промпт для контентной картинки | `topic`, `paragraph`, `image_style` |

Каждый шаблон существует в глобальной версии (`site_id IS NULL`) и может быть
переопределён для конкретного сайта. Разрешение: сначала ищется запись сайта, иначе
берётся глобальная.

**Экран «Промпты» обязателен для admin и содержит кнопку «Тест»** — прогон шаблона на
выбранном сайте с показом отрендеренного промпта, ответа модели и потраченных токенов,
без сохранения результата. Без этого отладка качества текстов будет вслепую: это
единственный инструмент, заменяющий сегодняшний диалог с агентом.

## 8. Процесс «Статьи» в сервисе

1. Менеджер: **Статьи → Новая партия**, выбирает сайт и количество N.
2. Celery `generate_topics`: тянет `GET /api/v1/staticpages/?page=N` постранично,
   отбирает страницы с префиксом `articles_url_prefix`, собирает существующие
   заголовки. В промпт `topics` уходят три вещи: **`site_description`** (о чём сайт,
   какая тематика, какая аудитория), **`tone_of_voice`** и список существующих
   заголовков. Тематику задаёт именно `site_description` — по одному лишь домену и
   списку прошлых статей модель промахивается: у сайта строительной базы и у сайта
   производителя смесей темы разные, хотя рубрика называется одинаково. Ответ модели —
   JSON-массив тем. Локально отбрасываются темы, чей нормализованный заголовок
   пересекается с существующими. Батч переходит в `topics_review`.
3. Экран партии: список тем, каждую можно отредактировать, удалить или добавить свою.
   Кнопка **«Запустить»**.
4. Celery `run_batch` → по одной задаче `build_article` на тему. Внутри каждой:
   - эталон берётся из кеша карточки сайта (`reference_html`), к сайту за ним не ходим;
     число контентных картинок равно `reference_images` — сколько `<img>` в эталоне,
     столько и генерируется;
   - RouterAI по промпту `article_body` возвращает HTML с уже проставленными путями
     `/media/uploads/article-img/article_{article_id}-{k}.webp`;
   - по каждому абзацу-иллюстрации — промпт `content_image` → RouterAI images →
     центральный кроп до нужного соотношения → ресайз до 1600px → webp q82 →
     **наложение водяного знака сайта** → `filemanager.upload_file` в `uploads/article-img/`;
   - обложка: промпт `cover` → та же генерация **без водяного знака**;
   - `POST /api/v1/staticpages/` с `published: false`, `parent`, `wide_view: true`,
     `use_editor: false`, `meta_*`; slug обрезается до 70 символов (для ветки
     `articles` — до 50);
   - обложка прикрепляется `PATCH` в поле `teaser_image` созданной страницы;
   - перед созданием страницы url сверяется со списком уже существующих — дубль
     пропускается, как в `publish_articles.py`.
5. Экран партии показывает прогресс по каждой статье, ссылку на созданный черновик и
   текст ошибки при неудаче; кнопка «Повторить» перезапускает одну статью.

## 9. Процесс «Строители» — план 2

Фиксируется здесь, чтобы модель данных плана 1 не пришлось ломать.

Загрузка выгрузки Яндекс.Карт (xlsx) через UI → импорт с фильтрами регион/сфера →
скрейпинг сайтов компаний ради маркетингового текста → RouterAI переписывает текст →
подстановка в `builder_template_html` → создание страницы черновиком → создание
карточки-тизера в `addresses-services` с `category`/`city`/`location` сайта.

Схема таблицы `companies` переносится из `execution/db.py` с добавлением `site_id` и
статуса публикации. Существующая `execution/data/companies.db` мигрируется в Postgres
разовым скриптом — сервис должен знать, кто уже выложен, иначе дедуп сломается.

## 10. Поверхность API

Всё под `/api`, всё кроме `/auth/login` требует авторизации.

| Метод | Путь | Роль | Назначение |
|---|---|---|---|
| POST | `/auth/login`, `/auth/logout` | — | вход/выход |
| GET | `/auth/me` | обе | профиль |
| GET | `/sites` | обе | список активных сайтов (без токенов) |
| GET/POST/PUT/DELETE | `/admin/sites` | admin | карточка сайта, токен шифруется, отдаётся маскированным |
| POST | `/admin/sites/{id}/watermark` | admin | загрузка PNG водяного знака |
| POST | `/admin/sites/{id}/sync` | admin | проверка токена + подтягивание раздела и эталона: возвращает `articles_url_prefix`, число статей в разделе и число картинок в эталоне |
| GET/POST/PUT/DELETE | `/admin/users` | admin | пользователи, последний админ не удаляется |
| GET/PUT | `/admin/settings` | admin | настройки RouterAI, секреты маскированы |
| GET/PUT | `/admin/prompts` | admin | шаблоны промптов |
| POST | `/admin/prompts/test` | admin | тестовый прогон шаблона |
| GET/POST | `/article-batches` | обе | список партий, создание |
| GET | `/article-batches/{id}` | обе | партия + темы + статьи |
| PUT | `/article-batches/{id}/topics` | обе | сохранение согласованного списка тем |
| POST | `/article-batches/{id}/run` | обе | запуск генерации |
| POST | `/articles/{id}/retry` | обе | повтор одной статьи |
| GET | `/jobs` | обе | журнал задач с фильтрами |
| GET | `/tasks/{task_id}/status` | обе | обёртка над `AsyncResult` |

Ошибки — единым форматом `{"detail": "..."}` через `HTTPException`; на фронте
axios-интерцептор: `401` → `/login`, `403` → «нет доступа», прочее → `message.error`.

## 11. Структура фронтенда

```
/login
/articles              Партии статей          (обе роли, дефолтная страница)
/articles/:id          Согласование тем и прогресс партии
/builders              Строители              (план 2, в плане 1 — заглушка)
/jobs                  Журнал задач
──────────── admin-only ────────────
/admin/sites           Сайты
/admin/prompts         Промпты
/admin/settings        Настройки RouterAI
/admin/users           Пользователи
```

CRUD-экраны — `Table` + `Modal` + `Form`, как в обоих образцах. Экран партии —
единственный без прямого аналога: список тем с инлайн-редактированием (`Table` с
редактируемой ячейкой) до запуска, после запуска — тот же список со статусом,
ссылкой на черновик и кнопкой повтора. Обновление — поллинг раз в 5 секунд, пока в
партии есть статьи в `generating`; интервал снимается при размонтировании.

## 12. Фоновые задачи, журнал и стоимость

Каждая постановка задачи создаёт запись `job_runs` (тип, сайт, параметры, автор,
`celery_task_id`). Каждый вызов RouterAI пишет `llm_usage` со стоимостью из
`usage.cost` (текст) или из ответа images. Экран «Журнал» показывает список задач со
статусом и суммой расхода за период — при цене ≈16.8 единицы за картинку в качестве
`high` расход надо видеть до того, как он станет сюрпризом.

Celery-beat в плане 1 не нужен — периодических задач нет, все запускаются из UI.

## 13. Тестирование

- **Backend** — `pytest` + `fastapi.testclient.TestClient`: коды ответов,
  сериализация, отказ по роли, маскирование секретов в `GET /admin/sites` и
  `GET /admin/settings`, шифрование/расшифровка, разрешение промпта
  «сайт → глобальный», кроп и водяной знак (Pillow, без сети), сборка payload
  публикации.
- **Внешние HTTP** (RouterAI, API сайтов) всегда замоканы — ни один тест не ходит в
  сеть. Реальные вызовы проверяются вручную кнопками «Тест» и
  «Проверить и синхронизировать».
- **Frontend** — без модульных тестов, как в обоих образцах; проверка вручную через
  дев-сервер по завершении каждого экрана.

## 14. Деплой

VPS компании, docker compose. `docker-compose.yml` (dev, с hot-reload) и
`docker-compose.prod.yml` (сборка фронта в nginx) — по образцу `inntec-inbox`, включая
разовый сервис `migrate` с `service_completed_successfully`, чтобы `api` и `worker` не
гонялись за одной DDL-транзакцией. `DEPLOY.md` пишется по образцу того же проекта.

Тома: `postgres_data`, `redis_data`, `media` (водяные знаки и локальные копии
сгенерированных картинок).

## 15. Риски

1. **Качество текста.** Главный риск. Сегодня тексты пишет агент в диалоге, с
   уточнениями; в сервисе это один промпт. Первые статьи почти наверняка окажутся хуже
   ручных. Смягчение: экран «Промпты» с кнопкой «Тест» и промпты, переопределяемые
   на уровне сайта. Приёмка плана 1 включает сравнение сгенерированной статьи с уже
   опубликованной эталонной.
2. **Стоимость картинок.** 40–140 секунд и ≈5.4–16.8 единицы за штуку. Партия из 10
   статей по 3 картинки плюс обложка — 40 генераций. Смягчение: `image_quality` по
   умолчанию `medium`, учёт в `llm_usage`, показ суммы в журнале.
3. **Публикация не на тот сайт.** 10+ сайтов, общий доступ. Смягчение: домен
   подтверждается на экране запуска партии, всё создаётся `published: false`.
4. **Расхождение с реальным API сайтов.** Поведение проверено только на
   stroybaza-samara.ru. Смягчение: кнопка «Проверить и синхронизировать» на карточке
   сайта делает реальные запросы (раздел, эталон) и показывает результат до того, как
   менеджер запустит партию.
5. **Смена `ENCRYPTION_KEY`** делает все токены нечитаемыми. Смягчение: перенесённый
   из образца `SecretDecryptionError` с внятным текстом вместо тихого пустого значения.
6. **Устаревший кеш эталона.** Эталонную статью отредактировали на сайте, а в карточке
   лежит прежний HTML — новые статьи пойдут по старой разметке. Смягчение: на карточке
   видно время последней синхронизации, обновление в одну кнопку. Автоматически кеш не
   инвалидируется: сайт не сообщает об изменениях, а опрашивать его ради этого незачем.
