# Публикация статей в раздел `articles`

## Задача

В карточке сайта есть настройка «Куда публиковать» с двумя значениями —
`pages` (статичные страницы, `/api/v1/staticpages/`) и `articles` (отдельный
раздел, `/api/v1/articles/`). Вторая ветка никогда не была реализована.

Поле `publish_target` заводилось вместе с моделью сайта (план 1) и попало во
все слои — модель, схему API, селект в форме сайта, — но в логике читалось
ровно в одном месте: `ArticleBuilder._slug_limit` выбирало по нему длину
обрезки слага (50 вместо 70). Всё остальное безусловно ходило в staticpages.
Константа `ARTICLES_PATH = "/api/v1/articles/"` была объявлена в
`app/sites/client.py` и не использовалась нигде.

Практический результат: выбрав «Раздел articles», менеджер получал статьи в
статичных страницах — просто с более коротким слагом. Настройка выглядела
рабочей и молча делала не то. Это хуже, чем её отсутствие.

Требование владельца: ветку доделать; при выборе «статей» в карточке сайта не
должно быть поля родительской страницы — раздел у этого движка известен
заранее.

## Что выяснено про `/api/v1/articles/` (живая проверка, union63.ru, 2026-09-23)

Эндпоинт рабочий, в нём 12 статей. `Allow` на списке — `GET, POST`, на
детальном — `GET, PUT, PATCH, DELETE`. `OPTIONS` отдаёт схему записи:

| поле | тип | обязательное | ограничение |
|---|---|---|---|
| `title` | string | да | 255 |
| `teaser` | string (HTML) | да | — |
| `body` | string (HTML) | да | — |
| `label` | string | да | 60 |
| `slug` | slug | да | **50** |
| `image` | image upload | нет | 100 |
| `published`, `wide_view`, `use_custom_form` | boolean | нет | — |
| `meta_description`, `meta_keywords` | string | нет | — |
| `related_products`, `related_products_title`, `related_productset` | — | нет | — |

Три отличия от staticpages определяют всю работу:

1. **Поля `url` нет вообще.** Адрес собирает сам движок: `/articles/<slug>/`.
   Проверено — `https://union63.ru/articles/zashita-drevesiny-zhivica/` отдаёт
   200. Мы пишем только слаг. Отсюда же и отсутствие родителя: класть статью
   некуда, кроме как в раздел, который у движка один.
2. **Обложка — поле `image`**, а не `teaser_image`. Механика та же
   (Django ImageField, только multipart, строкой-путём не задаётся).
3. **`label` и `teaser` обязательны**, а аналога в staticpages у них нет.
   Ограничение `slug` — 50 символов, что подтверждает уже захардкоженный
   `SLUG_LIMIT_ARTICLES` (самый длинный слаг на сайте — ровно 50 символов).

## Решение

### Цель публикации как объект, а не как `if` в восьми местах

`publish_target` влияет на восемь точек: источник эталона при синхронизации,
сбор заголовков для генерации тем, проверка «эталон синхронизирован», дедуп
по уже существующим статьям, создание записи, прикрепление обложки, PATCH
текста при перегенерации, длина слага. Ветвление в каждой из них разъедется
при первой же правке.

Поэтому вводится `app/sites/target.py`: `PagesTarget` и `ArticlesTarget` с
общим интерфейсом поверх `SiteClient`. `ArticleBuilder`, `sync_site_reference`
и задача генерации тем работают с целью, а не с `publish_target` напрямую;
`site_client` остаётся у билдера только для загрузки файлов через filemanager
— он общий для обеих веток и к записи страницы отношения не имеет.

Интерфейс цели:

```
url_prefix                     префикс публичного адреса раздела
slug_limit                     70 | 50
list_existing()                [{id, title, slug, url}] — существующие записи
reference(ref_id)              {html, label} — эталон
public_path(slug)              путь статьи на сайте
create(article)                {id, url} — черновик
update_text(remote_id, ...)    PATCH текста/заголовка/меты
set_cover(remote_id, ...)      обложка
labels()                       рубрики раздела (пусто у pages)
```

`list_existing` мемоизируется на время жизни цели (одна цель — одна статья):
дедуп и выбор рубрики спрашивают один и тот же список, ходить за ним на сайт
дважды незачем.

### Префикс `/articles/` — константа в коде

Для `pages` префикс по-прежнему вычисляется из url родительской страницы при
синхронизации и лежит в `articles_url_prefix`: раздел там произвольный, и
только сайт знает, где он. Для `articles` раздел задан движком, вычислять
нечего — `ARTICLES_URL_PREFIX = "/articles/"` живёт в коде,
`articles_url_prefix` у таких сайтов остаётся пустым и не читается.

Из этого следует, что проверка «эталон синхронизирован» не может опираться на
непустой `articles_url_prefix`, как раньше: для ветки `articles` признак
синхронизации — заполненные `reference_html` и `reference_images`.

Миграция не нужна: ни одного нового поля в `sites` эта работа не добавляет.

### `label` — выбор из рубрик, которые уже есть на сайте

Рубрика обязательна, и выдумывать её свободно нельзя: на сайте появятся
почти-дубли («О материалах» и «Про материалы»). Решение владельца — модель
выбирает из списка рубрик, уже существующих в разделе. Список собирается из
того же `list_existing()`, отдельного поля в карточке сайта не заводим: список
живёт на сайте, и кеш в карточке — лишний источник расхождения.

Выбор делает отдельный дешёвый промпт `article_label` (`topic`, `title`,
`labels`), а не расширение `article_body`. Причина: `article_body` — тонко
настроенный контракт, у сайтов бывают свои переопределения промпта, и добавление
поля в его JSON молча не доедет до переопределённых шаблонов.

Ответ модели сверяется со списком без учёта регистра. Не совпал — берём
рубрику эталонной статьи (она всегда в списке, эталон обязателен), а если и её
нет — первую из списка. Обрезка до 60 символов. Пустой список рубрик означает
раздел без единой статьи — это же означает и отсутствие эталона, то есть до
сборки дело не дойдёт.

### `teaser` — из `meta_description`

Решение владельца: `<p>{meta_description}</p>`. Промпт не трогаем, лишних
токенов не тратим, и это совпадает с тем, что на сайте лежит сейчас — тизеры
существующих статей union63.ru и есть одно предложение-описание. Пустой
`meta_description` (модель может его не вернуть — `_generate_body` требует
только `html`) → в тизер идёт заголовок: поле обязательное, пустым его слать
нельзя. Текст экранируется как HTML-содержимое.

### Дедуп

У `pages` дубль ловится по совпадению url в списке страниц раздела. У
`articles` url в списке нет — сравниваем слаги. Собственный частичный индекс
`uq_article_site_slug` (site_id, slug) работает для обеих веток без изменений.

## Настройки сайта

- «ID родительской страницы раздела» показывается и обязателен только при
  `publish_target = pages`. При `articles` поле скрыто, а его значение
  обнуляется при сохранении — иначе у сайта останется висеть id страницы,
  которая ни на что не влияет, и следующий читатель карточки будет гадать.
- Синхронизация требует родителя тоже только для `pages`.
- Колонка «Раздел статей» для `articles` показывает `/articles/` без «parent N».
- `publish_target` валидируется моделью: допустимы только `pages` и `articles`.

## Что осталось за рамками

`related_products`, `related_products_title`, `related_productset` и
`use_custom_form` не заполняются — это товарная обвязка карточки статьи, к
генерации контента отношения не имеет. `created` не передаём: движок ставит
сам.
