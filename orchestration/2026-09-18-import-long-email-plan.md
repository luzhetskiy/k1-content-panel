# План: импорт падает на склеенных email (2026-09-18)

## Инцидент
Загрузка «0509_Яндекс_и_Дом_новый_формат_объединено_по_эталону.xlsx» (5083 строки)
упала целиком: `StringDataRightTruncation: value too long for type character varying(200)`.
Транзакция откатилась — пул кандидатов не изменился (проверено на проде).

Причина: в новом формате колонка «Email с сайта компании» содержит несколько адресов
через `;` (489 строк) или `,` (180 строк). Парсер отрезал только по `,` — у 9 компаний
строка из `;`-адресов длиннее 200 символов (до 796). На странице email выводится одной
ссылкой `mailto:`, так что список адресов сломал бы и её.

Тесты идут на SQLite, который не проверяет длину VARCHAR, — поэтому переполнение
ловит только прод, а пользователь видит безликое «проверьте данные файла».

## Решения
1. `import_xlsx.py`: email — первый адрес, разделители `,` и `;`.
2. `imports.py`: до записи сверить длины значений с `String(n)` колонок
   `CompanyCandidate`; при превышении — импорт `failed`, в БД ничего не пишется,
   сообщение называет компанию, поле и длину (первые 3 случая + «и ещё N»).
   Общий except вокруг commit остаётся для прочих сбоев.

## Шаги (TDD)
1. Тест парсера: `a@x.ru;b@y.ru` → `a@x.ru`. Правка парсера.
2. Тест импорта: слишком длинное значение → `failed`, сообщение с названием
   компании и полем, кандидатов 0. Реализация проверки.
3. Полный регресс бэкенда; прогон реального файла через парсер + проверку.
4. Коммит, деплой (с согласия), повторная загрузка файла пользователем.
