# Раздел «Строители» — импорт и партии — дизайн

Дата: 2026-08-06
Статус: на утверждение
Базовые документы: `directions/2026-08-04-content-service-design.md` (§9 — общая
рамка плана 2), `directions/project-overview.md`, `execution/step1_import_yandex.py`,
`execution/db.py`

Уточняет и раскрывает §9 документа `2026-08-04-content-service-design.md`: как именно
устроен импорт выгрузки Яндекс.Карт и нарезка партий строительных компаний в веб-сервисе.

## 1. Что меняется относительно текущего CLI-процесса

| Аспект | Сегодня (CLI, `step1_import_yandex.py`) | В сервисе |
|---|---|---|
| Источник сферы | Оператор передаёт `--sphere` из фиксированного списка `directions/spheres.md`; колонка «Категории» только фильтрует строки по ключевым словам (`SPHERE_KEYWORDS`) | Сфера — фактическое значение из колонки D «Категории» файла, оператор выбирает из выпадающего списка обнаруженных значений |
| Источник региона | Оператор передаёт `--region` из фиксированного списка `directions/regions.md`; колонка «Регион»/«Город» только фильтрует строки | Регион — фактическое значение из колонки G «Регион» файла |
| Дедуп по сайту | Опционален, включается флагом `--exclude-existing`, проверка глобально по всей `companies.website` | Обязателен всегда, в рамках конкретного `site_id` — одна и та же компания может быть отдельно предложена под разные сайты |
| Ранжирование | Сортировка по убыванию `Отзывов` | Без изменений — сортировка по убыванию `Отзывов` |
| Загрузка файла | Файл лежит на диске, путь передаётся аргументом CLI | Загрузка xlsx через UI, upsert в общий пул кандидатов |
| Согласование партии | Отсутствует — что отобрал скрипт, то и обрабатывается | Экран превью: менеджер видит отобранный список, может вычеркнуть/добрать компанию перед запуском (аналог `topics_review` у статей) |
| «Уже добавленные» компании | `execution/data/companies.db` | Мигрируются в Postgres, один раз, разовым скриптом |

`directions/spheres.md` и `directions/regions.md` теряют роль источника истины для новых
партий (справочник теперь — сам файл) и остаются как исторический контекст/подсказка,
какие значения встречались раньше.

## 2. Модель данных

```
company_imports      журнал загрузок xlsx: файл, кто, когда, сколько строк, статус
company_candidates   общий пул кандидатов (upsert по site_key), не привязан к партии
company_batches      партия: сайт, регион, категория, нормализация, статус
companies            компании конкретного сайта (перенос execution/db.py + site_id, batch_id)
company_info         как в execution/db.py, привязка через companies.id
generated_content    как в execution/db.py, привязка через companies.id
```

### `company_imports`

| Поле | Назначение |
|---|---|
| `id`, `filename`, `uploaded_by`, `uploaded_at` | идентификация загрузки |
| `row_count`, `matched_count`, `error_count` | статистика парсинга, для отчёта оператору |
| `status` | `parsed` / `failed` |
| `error_message` | причина отказа, если парсинг не прошёл (нет обязательных колонок и т.п.) |

Импорт — только журнал. Партии не ссылаются на конкретный `import_id`: они всегда
работают с текущим состоянием `company_candidates`.

### `company_candidates`

| Поле | Назначение |
|---|---|
| `id` | — |
| `site_key` (UNIQUE) | нормализованный адрес сайта компании (без схемы/`www`/слэша/регистра) — ключ upsert |
| `website_raw` | исходный URL из файла, для отображения |
| `name`, `region_raw`, `category_raw`, `city`, `address`, `phones`, `email` | из соответствующих колонок |
| `rating`, `reviews_count`, `ratings_count` | из колонок «Рейтинг», «Отзывов», «Оценок» |
| `lat`, `lon`, `yandex_url` | как в текущей выгрузке |
| `raw_row_json` | вся строка файла целиком, для отладки расхождений |
| `last_seen_import_id` | последний импорт, в котором строка встретилась (для диагностики, не для фильтрации) |
| `updated_at` | время последнего upsert |

`category_raw` хранит **только первый сегмент** значения колонки «Категории» до
первого символа `|`, обрезанный по пробелам. Пример: ячейка
`"Строительство дачных домов и коттеджей | строительство бань и саун | строительная компания"`
даёт `category_raw = "Строительство дачных домов и коттеджей"`. Всё после первого `|` —
уточнения источника, которые только вносят путаницу в справочник категорий, и не
сохраняются отдельно (полная строка всё равно доступна в `raw_row_json`).

Строки без сайта не попадают в пул вовсе (аналог текущего `--require-site`,
без опции отключить — исключений не было и не предполагается).

### `companies` (перенос `execution/db.py`, расширение)

Добавляются `site_id` (FK), `batch_id` (FK), `candidate_id` (FK, nullable — `NULL`
для строк, перенесённых из старого CLI без привязки к конкретному кандидату),
`category_normalized`, `teaser_category_id`, `teaser_city_id`, `teaser_location_id`,
`status` (`draft` / `scraped` / `generated` / `published` / `failed`).

Уникальность — `(site_id, site_key)`, а не глобально по `website`, как раньше: это и
есть дедуп «в рамках сайта».

### `company_batches`

| Поле | Назначение |
|---|---|
| `site_id` | — |
| `region_raw`, `category_raw` | выбраны из facets текущего пула кандидатов |
| `category_normalized` | введено оператором вручную при создании партии, каждый раз заново (без сохранения на будущее — сознательное решение, см. §4) |
| `teaser_category_id`, `teaser_city_id`, `teaser_location_id` | введены оператором вручную при создании партии |
| `requested_count` | запрошенное N |
| `status` | `selection_review` → `running` → `done` / `failed` |

## 3. Импорт xlsx

`POST /api/company-imports` (multipart xlsx):

1. Парсинг переиспользует логику `step1_import_yandex.py` (`build_header_map`,
   разбор колонок), портированную в `app/companies/import_xlsx.py`. Обязательные
   колонки — как сейчас: Название, Регион, Город, Категории, Сайт.
2. Для каждой строки: нормализация `site_key`; если сайта нет — строка отбрасывается
   и попадает в `error_count`, но не роняет весь импорт.
3. `category_raw` вычисляется по правилу «первый сегмент до `|`» (см. §2).
4. **Upsert по `site_key`** в `company_candidates`: новая компания — вставляется;
   существующая — обновляются `region_raw`, `category_raw`, `rating`, `reviews_count`,
   `ratings_count`, `name`, `updated_at`. Это соответствует поведению текущего
   `db.upsert_company` (`ON CONFLICT(website) DO UPDATE ...`), перенесённому на новый
   пул кандидатов.
5. Внутри одного файла возможны дубли по `site_key` (несколько строк на одну и ту же
   компанию) — сворачиваются в одну до upsert, как сейчас (`seen_sites`).

`GET /api/company-imports/facets?site_id=` — различные текущие значения `region_raw`
и `category_raw` в пуле кандидатов, ещё не взятых для данного `site_id` (чтобы в
выпадающем списке не мелькали категории, где для этого сайта уже нечего предложить,
хотя пустой список тоже валиден — просто предупреждение в UI). Это и есть «справочник
из xlsx», заменяющий собой `spheres.md`/`regions.md` для новых партий.

## 4. Создание партии и превью

`POST /api/company-batches`: `{site_id, region_raw, category_raw, category_normalized,
teaser_category_id, teaser_city_id, teaser_location_id, count}`.

Оператор вводит `category_normalized` и три teaser id заново при каждой партии, даже
если такая пара (`site_id`, `category_raw`) уже встречалась раньше — постоянного
маппинга сервис не хранит. Это сознательный выбор: проще и прозрачнее, чем скрытое
автоподставление, которое незаметно разойдётся при переименовании категории на сайте.

Сервер:

1. Фильтрует `company_candidates` по `region_raw`, `category_raw`.
2. Исключает кандидатов, чей `site_key` уже есть в `companies` для этого `site_id`
   (дедуп в рамках сайта).
3. Сортирует оставшихся по убыванию `reviews_count`, берёт первые `count`.
4. Создаёт `company_batch` (`status = selection_review`) и черновые `companies`
   (`status = draft`) для отобранных кандидатов, со ссылкой на `candidate_id`.

Экран превью (`GET /api/company-batches/{id}`) показывает список; `DELETE
/api/company-batches/{id}/companies/{company_id}` убирает компанию из партии.
`POST /api/company-batches/{id}/companies/next` добирает следующую по рейтингу
компанию из оставшихся подходящих кандидатов — на случай, если после вычёркивания
осталось меньше, чем нужно (аналог механики «добора тем» из партий статей,
commit `0088e6a`).

`POST /api/company-batches/{id}/run` переводит партию в `running` и ставит по одной
Celery-задаче на компанию.

## 5. Генерация (без изменений по сути, порт существующих шагов)

На каждую компанию в партии:

1. Скрейпинг сайта компании ради маркетингового текста (порт `step2_scrape_company.py`).
2. RouterAI переписывает текст по промпту (аналог `step3`), сохраняя достоверные поля
   из Яндекс-выгрузки нетронутыми — перенос принципа `YANDEX_INFO_FIELDS`: RouterAI не
   имеет права переписывать контакты/адрес/координаты, только маркетинговый текст.
3. Подстановка в `builder_template_html` сайта (карточка `sites`).
4. Создание страницы черновиком (`published: false`) через `site_client`.
5. Создание карточки-тизера в `/api/v1/addresses-services/` с `teaser_category_id`,
   `teaser_city_id`, `teaser_location_id` партии.
6. `companies.status → generated` при успехе, `failed` + текст ошибки при неудаче;
   повтор — по одной компании, как `POST /articles/{id}/retry`.

Публикация — по-прежнему отдельное ручное действие в админке сайта.

## 6. Миграция старых CLI-данных

Разовый скрипт `execution/backend/migrate_companies_from_cli.py`:

1. Читает `execution/data/companies.db` (`companies`, `company_info`,
   `generated_content`).
2. Для каждой записи `generated_content.target_site` резолвит `site_id` по
   `sites.domain`. Записи без сопоставимого сайта — в отчёт, не переносятся молча.
3. Создаёт `companies` (`site_id`, `candidate_id = NULL`, `status` по `published`),
   переносит `company_info`/`generated_content` как есть.

Без этого шага дедуп по `(site_id, site_key)` не увидит уже опубликованные вручную
компании и предложит их повторно в первой же партии — шаг обязателен до включения
раздела «Строители» в проде.

## 7. Именование файлов изображений

Компании получают отдельный префикс загружаемых изображений — `cp-company-{id}-{n}.webp`
— не пересекающийся ни со старой CLI-схемой (`builder_*`), ни со схемой статей
(`cp-article-*`, см. commit `46323ab`, инцидент с коллизией `article_{N}-{k}.webp`).

## 8. Тестирование

- Парсинг xlsx: обязательные колонки, разбор `category_raw` по `|`, дубли внутри файла.
- Upsert: повторная загрузка обновляет рейтинг/отзывы существующего кандидата, не
  создаёт дубль по `site_key`.
- Facets: не показывают категорию/регион, где для сайта нечего предложить (все уже
  взяты).
- Отбор партии: фильтр региона+категории, исключение уже взятых для `site_id`,
  сортировка по `reviews_count`, добор при нехватке после вычёркивания.
- Миграция: идемпотентность повторного запуска, корректный резолв `site_id` по домену.
- Внешние вызовы (RouterAI, site API) — замоканы, как в разделе «Статьи».

## 9. Открытые вопросы

Нет открытых. Решения по итогам обсуждения 2026-08-06: сфера/регион — из файла, без
фиксированных справочников; дедуп — по сайту в рамках `site_id`; ранжирование — без
изменений (по `Отзывов`); импорт и партия — разные сущности, импорт работает в режиме
upsert в общий пул; нормализация категории и teaser id вводятся вручную при каждой
партии без сохранения маппинга; нужен шаг превью с возможностью добора.
