# Раздел «Проекты домов»

## Задача

На части сайтов есть раздел проектов домов (на stroybaza-samara.ru —
`/addresses/projects/`). Раздел клонируется с сайта на сайт, конечные страницы
на разных сайтах совпадают один в один. Нужен рерайт описаний этих страниц в
панели — чтобы тексты на сайтах различались.

Требования владельца:

- **Проект** — как в «Метатегах категорий»: выбирается заведённый сайт,
  менеджер указывает id родительской страницы, под которой лежат страницы
  проектов.
- В проекте — кнопка **«Запустить рерайт»**.
- Переписывается **только описательная часть**. Параметры, характеристики и
  прочие факты о проекте не меняются.
- **Объём** — примерно как был, ±5–10 %.
- Дата и время рерайта запоминаются, **повторный рерайт возможен**.

Решения владельца по итогам обсуждения (2026-10-18, не переспрашивать):

- повторный рерайт — **от оригинала**, а не от текущего текста на сайте
  (исключение — правка руками, см. «Ход запуска», шаг 4.3);
- результат пишется **сразу на сайт**, без черновика в панели;
- при запуске — выбор **«Только новые» / «Все заново»**, у каждой страницы —
  своя кнопка «Переписать»;
- **чистый рерайт**: города сайта и других новых сведений в тексте нет.

## Что проверено до проектирования (2026-10-18, stroybaza-samara.ru)

- Родитель раздела — staticpage **15** «Проекты домов», url `/addresses/projects/`.
- Дети — **56 страниц**, url **`/pr/...`**, а не `/addresses/projects/...`:
  отбор по префиксу url (как у статей) не годится.
- Список `/api/v1/staticpages/` отдаёт только `id, title, url`; `parent` есть
  только в карточке `/api/v1/staticpages/{id}/`, фильтр `?parent=` сайт
  игнорирует. Значит, отбор детей — карточка каждой страницы сайта: на Самаре
  265 страниц, ~265 запросов, 1–2 минуты.
- Ещё две страницы `/pr/` (id 76 и 104) — с `parent: null`. В раздел они не
  попадают; если это проекты — их надо завести под родителя в админке сайта.
- Разметка у всех 56 страниц одна. Поле `text` — HTML из секций:
  - `section.gallery` — фото;
  - `section.project-chars` — «Характеристики проекта» (`ul.char`: материал
    стен, этажность, площадь, спальни, кровля, фасад, пристрой);
  - `section.project-description` → **ровно один** `div.product-info__text` —
    «Описание проекта»: `p`, `h3` «Ключевые преимущества и удобства», `ul/li`,
    `br`;
  - баннер каталога, `section.layout` — планировки, кнопки, `section.cost-building`
    с шаблонным тегом `{% custom_form "forma-rasschet" %}`.
- Видимый текст описания — 1 393–2 949 символов, медиана 2 182.
- В самом описании тоже есть факты: «82.64 м²», «терраса 9.06 м²», «11×9 м»,
  «145,4 м²», «монолитная железобетонная плита», «металлочерепица».
- Разметка двух видов: у одних страниц — с переносами и отступами, у других —
  в одну строку, `<br />` вместо `<br>`. Любая пересериализация HTML (BeautifulSoup
  и т.п.) изменила бы страницу целиком.

## Решение

### Подход

**Меняется только содержимое блока описания.** Код находит в HTML страницы
`div.product-info__text` внутри `section.project-description`, отдаёт модели
только его внутренний HTML и вставляет ответ обратно **по позициям в исходной
строке**: всё до открывающего тега блока и после его закрывающего тега остаётся
байт в байт. Модель не видит характеристик, галереи, планировок и формы и не
может их испортить. Один вызов LLM на страницу.

Отклонены:

- весь HTML страницы модели с инструкцией «перепиши только описание» — риск
  переформатирования разметки и порчи `{% custom_form %}`, втрое больше токенов;
- рерайт по абзацам отдельными вызовами — теряется связность текста, 10–15
  вызовов на страницу.

### Данные

**Проект = существующая карточка сайта** (`sites`), как в «Метатегах».
Новые поля:

- `projects_enabled` — сайт добавлен в раздел;
- `projects_parent_id` — id родительской staticpage (на Самаре — 15).

При добавлении проекта панель читает родительскую страницу с сайта и показывает
её название — менеджер видит, что не ошибся с id. Страницы нет — проект не
сохраняется, ошибка «страница {id} не найдена на сайте».

**`house_project_pages`** — строка на страницу проекта:

- `site_id`, `remote_id`, `title`, `url`;
- `original_html` — внутренний HTML блока описания до нашего первого рерайта;
  все повторы делаются от него;
- `rewritten_html` — последняя наша версия;
- `status`: `new` → `queued` → `in_work` → `done` | `failed`; `skipped` с
  `skip_reason` («нет блока описания» / «удалена на сайте»);
- `rewritten_at` — дата и время последнего успешного рерайта, `rewrite_count`;
- `error_text`, `started_at`, `updated_at`.

Уникальность — `(site_id, remote_id)`.

**`project_rewrite_runs`** — запуск по проекту: `site_id`, `mode` (`new` |
`all`), `total`, `job_run_id` (расход LLM запуска — одна строка журнала),
`created_by_id`, `started_at`, `finished_at`, `error_text`. Метка «Последний
рерайт …» у проекта — максимальный `rewritten_at` его страниц.

### Ход запуска («Запустить рерайт»)

1. **Синхронизация** (задача Celery, не в запросе API — 1–2 минуты): список
   страниц сайта, затем карточка каждой; отбираются **прямые дети**
   `projects_parent_id`. Новые страницы добавляются как `new` (в том числе
   только что склонированные с другого сайта). Страницы, пропавшие с сайта или
   переехавшие к другому родителю, — `skipped`, «удалена на сайте»; из панели не
   стираются. У существующих обновляются `title` и `url`.
2. **Отбор:** режим «Только новые» — `new` и `failed`; «Все заново» — все,
   кроме `skipped`. Отобранным ставится `queued`, `total` запуска — их число.
   Отобрано ноль — запуск сразу завершается.
3. **Цепочка задач** (как в «Метатегах»): в Celery уходит задача только первой
   `queued` страницы, каждая по завершении ставит следующую страницу этого
   сайта. Проект занимает не больше одного слота воркера и не встаёт в очередь
   перед партиями статей.
4. **Задача страницы:**
   1. читает карточку страницы с сайта, находит блок описания; блока нет или их
      больше одного — `skipped`, «нет блока описания»;
   2. `original_html` пуст — в него сохраняется текущее содержимое блока;
   3. **правка руками после нас:** текущее содержимое блока не совпадает ни с
      `original_html`, ни с `rewritten_html` — его поправили в админке сайта,
      и оно становится новым `original_html` (иначе повтор от оригинала затёр
      бы, например, исправленную площадь). Сравнение — без учёта пробелов,
      переносов между тегами и `<br />` против `<br>`: админка переформатирует
      разметку при сохранении;
   4. LLM переписывает `original_html` по промпту `project_rewrite`, вызов с
      `reasoning: {enabled: false}`: скрытые рассуждения в «Метатегах» стоили в
      3–5 раз больше самого текста. Ответ — голый HTML, без JSON (в JSON модели
      оставляли неэкранированные кавычки внутри HTML);
   5. код проверяет результат (ниже); при нарушениях — один повтор с перечнем
      нарушений в промпте, затем `failed`, на сайт ничего не пишется;
   6. новый блок вставляется в HTML страницы, **прочитанный на шаге 4.1** — не
      в сохранённый когда-то, чтобы не затереть правки остальной страницы;
      PATCH поля `text` (`SiteClient.update_page_text(..., as_is=True)`: обычный
      вызов вырезает HTML-комментарии, а на странице есть `<!-- Хар-ки и
      описание -->`). Затем `rewritten_html`, `rewritten_at`, `rewrite_count + 1`,
      `status = done`.

**«Переписать» у страницы** — шаги 4.1–4.6 для одной страницы, без
синхронизации и без продолжения цепочки. Во время запуска по проекту недоступна.

### Правила рерайта

**Промпт `project_rewrite`** — в `PROMPT_KEYS` с объявленными
`PROMPT_VARIABLES`: `title`, `description_html`, `char_count` (видимый текст
оригинала), `site_name`, `tone_of_voice`, `violations` (нарушения первой
попытки). Сидится дефолтом, редактируется в
админке, переопределяется на сайт — как остальные. Содержание дефолта:

- переписать тот же смысл другими словами, другим порядком фраз и
  формулировками, без новых сведений;
- **не менять** числа, размеры, площади, материалы, конструктив, комплектацию —
  все факты о проекте;
- не добавлять город, регион, цены, сроки, гарантии и прочее, чего нет в
  оригинале;
- сохранить разметку: те же заголовки `h3`, столько же пунктов в списках,
  только теги оригинала, без атрибутов;
- объём — **«около {{ char_count }} символов»**: модели пишут длиннее
  просимого (см. SEO-тексты в `directions/2026-09-16-category-meta-design.md`);
  если на живой проверке выйдет систематически длиннее — цель в промпте
  снижается, как там.

**Проверки кода** (`app/house_projects/validate.py`):

| Проверка | Правило |
|---|---|
| Объём | видимый текст — в пределах ±10 % от оригинала |
| Только HTML | ответ начинается с `<` и кончается `>`: пояснения модели вокруг разметки на сайт не уходят |
| Числа | каждое число оригинала есть в тексте рерайта; `82.64` и `82,64` — одно число; `11×9` разбирается на 11 и 9; новых чисел от двух цифр и дробных нет (однозначные — пересказ: «в 2 уровня») |
| Структура | те же `h3` в том же порядке (по количеству), в каждом списке столько же `li`, что в оригинале; теги — только из оригинала |
| Отличие | доля 4-словных цепочек оригинала, повторённых в рерайте, — не больше 25 %; порог уточняется на живой проверке |

Материалы и конструктив («монолитная плита», «металлочерепица») код не сверяет —
их сохранность держится на промпте; числа — самая проверяемая часть фактов.
Новое однозначное число в рерайте не ошибка: модель пишет «в 2 уровня» вместо
«двухуровневая». Новое число от двух цифр или дробное — ошибка: это уже новый
факт («служит 100 лет», лишняя площадь); добавлено по ревью Task 3. В подсказке
на повтор пропавшее число пишется как в оригинале («21,17», а не «21.17»).

**Проба до реализации (2026-10-18, `openai/gpt-6-luna-pro`, 5 страниц
stroybaza-samara.ru, без записи на сайт):** объём 94–104 % оригинала, совпадение
4-словных цепочек 4–22 %, все числа и материалы на месте, разметка сохранена.
Одна страница из пяти с первой попытки сократила список с 11 пунктов до 8 —
проверка поймала, вторая попытка прошла. Вызов ≈ 0,24 ₽ (≈ 3 тыс. токенов
ответа без рассуждений).

### Интерфейс

Пункт меню **«Проекты домов»**, `/house-projects`.

**Список проектов:**

- «Добавить проект» — выбор сайта из заведённых, id родительской страницы;
  панель показывает название страницы для сверки;
- строка проекта: сайт, «Проекты домов (id 15)», «Переписано 40 из 56»,
  «Последний рерайт 18.10.2026 14:20» или «ещё не было»;
- кнопка **«Запустить рерайт»** — выбор режима: «Только новые (16)» / «Все
  заново (56)», число страниц видно до запуска (по данным последней
  синхронизации);
- во время запуска вместо кнопки — «Синхронизация…», затем «В работе: 12 из 56».
  Опрос сервера — как на странице партии. Повторный запуск во время работы — 409.

**Проект раскрывается в таблицу страниц:** название, ссылка на страницу, статус
(новая / в очереди / в работе / готово / ошибка / пропущена), дата последнего
рерайта, сколько раз переписана. Клик — карточка:

- «Оригинал» и «Сейчас на сайте» (последняя наша версия) в две колонки, объём
  каждой в символах;
- текст ошибки, если есть;
- кнопка **«Переписать»**.

В том же коммите — справка раздела в `help.tsx` и запись в `changelog.ts`, вид
`feature`.

### Сбои

- **Сайт** — сеть, 5xx: до 3 попыток с паузой 1 и 2 с, затем страница
  `failed`; 4xx не повторяется. Так же читается и синхронизация. PATCH текста
  повторять безопасно — дублей не создаёт.
- **Ошибка конфигурации** (нет ключа RouterAI, токен сайта не расшифровывается):
  упавшая страница и все оставшиеся в очереди получают этот текст, запуск
  закрывается.
- **LLM** — ошибка вызова: страница `failed`, цепочка идёт к следующей.
- **Синхронизация** упала (токен отклонён, сайт недоступен): запуск закрывается
  с текстом ошибки, статусы страниц не меняются.
- **Зависшие:** `in_work` дольше 25 минут показывается как зависшая, доступна
  кнопка «Переписать». Мягкий лимит задачи страницы — 1200 с: худший случай —
  чтение 3 × 60 с, два вызова LLM по 366 с (три попытки RouterAI), PATCH 3 × 60 с;
  обычно — минута.
- **Потерянные:** страница в `queued` без признаков жизни два часа (сообщение
  Celery потеряно, отдельный рерайт без запуска) проект не держит, показывается
  как зависшая и берётся режимом «Только новые».
- **Оборванная цепочка** (сообщение Celery потеряно, воркер перезапущен): 2 часа
  нет ни одной работающей страницы и ни одного изменения в очереди — запуск
  закрывается с пометкой «прерван», `queued` возвращаются в прежний статус
  (`done`, если страница уже переписывалась, иначе `new`), «Запустить рерайт»
  снова доступна.
- **Запуск завершён**, когда отобранных страниц в `queued`/`in_work` не осталось.
- **Расход LLM** — в `JobRun` / `LlmUsage`, как у статей и метатегов.

### Тесты

TDD, pytest, HTTP подменяется:

- поиск блока описания и вставка нового: HTML вне блока совпадает байт в байт
  на обоих видах разметки, `{% custom_form %}` цел; нет блока или два блока —
  `skipped`;
- проверки: объём на границах ±10 %, пропавшее число, `82.64` vs `82,64`,
  `11×9`, изменённое число `h3` и `li`, лишний тег, слишком похожий текст;
- правка руками после рерайта становится новым оригиналом; повтор без правки —
  от прежнего оригинала;
- синхронизация: только прямые дети, новые страницы, удалённые и переехавшие;
- режимы «новые» / «все», цепочка, завершение запуска, 409, зависшие,
  оборванная цепочка;
- разбор ответа LLM (голый HTML, обёртка ```html).

**Живая проверка** — локальный стенд (скилл `running-local-panel`), одна
страница stroybaza-samara.ru с настоящей моделью: читаем текст, сверяем объём и
факты, подбираем порог отличия. Запись на боевой сайт — только после
подтверждения владельца.

## Вне рамок

- Вложенные подразделы — берутся только прямые дети родительской страницы.
- Город и другие новые сведения в тексте.
- Черновики и ручная правка текста в панели (править руками — в админке сайта).
- Заголовок страницы, `meta_description`, `meta_keywords` — не меняются.
- Сверка рерайтов разных сайтов между собой — каждый сайт переписывается от
  своего оригинала независимо.
